# Changelog

Conventions: docs/21-changelog-conventions.md. One entry per distinct change, newest at the top.

2026-09-10, Phase 2 (T4): captured every destructive write's full before-state into the recovery bin, streaming so size is not a limit. Reason: docs/07 requires the bin to hold the before-state of anything deleted or overwritten regardless of operation size, which a return value cannot carry when the operation is larger than memory. The adapter now streams each record to a sink as it reads, keeping the adapter layer and the recovery store separate as docs/17 requires; the app supplies a sink backed by the staging area from T3, finalising into a real entry after the write commits and discarding otherwise. The sink sits outside the write's transaction on purpose, since a sink inside it would roll back along with the data it exists to preserve; that is why the caller must discard a capture whose write failed, and there is a test documenting exactly that. An insert streams nothing, and a capture that fails partway produces no entry at all rather than one that claims a before-state it does not hold. Updated docs/07-audit-log-and-recovery-bin.md.

2026-09-10, Phase 2 (T3): added the recovery bin store, its 30-day retention, the per-connection cap, and the staging area a large capture streams through. Reason: docs/01-prd.md rules out automatic rollback, so this store is what stands between a user and a mistake, and it has to exist before anything can capture into it. Purging clears a payload and marks the row rather than deleting it, per decision A, so the audit log's reference keeps resolving to "this existed and was purged on this date" and no audit entry ever has to be edited to record the loss. The clock is injected, so expiry is proven by advancing a fixed clock rather than waiting a month, as docs/18 requires. Per decision B a capture too large for memory streams into a staging area during the write's transaction and becomes a real entry only after it commits, with staged records discarded if it does not and swept at startup if a process died mid-write. Per decision D nothing purges an entry because its connection was deleted; the window runs its normal course. Updated docs/07-audit-log-and-recovery-bin.md and docs/15-data-model.md.

2026-09-10, Phase 2 (T2): captured before and after state on every write and moved the write record from phase 1's flat file to the audit log. Reason: docs/07 requires the log to hold both sides, and capturing them correctly is a per-operation question rather than one generic read. The capture happens inside the write's own transaction: a separate read beforehand would leave a gap in which the records could change, and the store would then hold something that was never what the write actually changed. An update reads its after-state back by primary key rather than by filter, because "set active to false where active is true" matches nothing once it has run and re-reading by filter would record that the records had disappeared; a table with no single-column primary key reports the after-state as unavailable rather than empty, since empty would read as the records having vanished. Captured values keep their types, unlike the preview which casts to text for display. Phase 1's command history is imported at startup rather than on the first write, so the audit log viewer will not look empty until the user happens to change something. Updated docs/05-confirmation-workflow.md and docs/07-audit-log-and-recovery-bin.md.

2026-09-10, Phase 2 (T1): added the engine-neutral captured-state types and the audit log store. Reason: three more adapters and the recovery bin all have to feed this, so its shape is settled before any of them exist rather than retrofitted into each. State is stored as JSON, a set of named values per record with each value keeping its own shape, so a SQL row and a MongoDB document are both representable without flattening a document into a grid it never had; the recovery bin is the only record of data that no longer exists, so losing the truth about what was stored is the one thing it cannot afford. The log is a SQLite table with bundled SQLite, sharing one file with the recovery bin so the reference between them is a real foreign key. Append-only is enforced by database triggers rather than by the discipline of the writing code, so a future code path that tries to edit or delete an entry cannot succeed whatever it intended. Size tiering follows docs/07: full state inline below the threshold, a sample plus a recovery reference above it, never both. Phase 1's command history imports as summary-only rows flagged as predating state capture, and the original file is left on disk untouched. Updated docs/15-data-model.md and docs/02-architecture.md.

2026-09-10, Phase 2: specified MongoDB's collection-level destruction and inferred schemas in the adapters document. Reason: docs/04 covered Mongo's document-level previews and transactions but said nothing about dropping or emptying a collection, and CLAUDE.md rule 2 forbids writing code against an engine's unspecified behaviour, so T12 could not have been built without this. Dropping previews the collection's inferred fields and document count with a warning that the collection itself goes; emptying previews the same without that warning. Also recorded that a document store's field list is always inferred from a sample and must never be treated as proof a field does not exist. Updated docs/04-database-adapters.md.

2026-09-10, Phase 1 (T14): packaged the app as a macOS bundle and disk image, and recorded the code signing gap. Reason: macOS packaging is a phase 1 deliverable (docs/03-phases-roadmap.md), and proving the packaging pipeline works now is worth more than discovering it does not in phase 3. The bundle is unsigned and not notarized, carrying only the ad-hoc signature Rust's linker produces, because signing requires a paid Apple Developer certificate. 2026-09-10, Phase 1 (T13): added the basic command history, appended after every attempted write. Reason: docs/03-phases-roadmap.md gives phase 1 a command history and defers the real audit log and recovery bin to phase 2, so this holds five fields and nothing more: recorded at, connection, operation type, intent summary, result. Stored as one JSON object per line so appending never rewrites the file and so it can be read with `cat` while there is no viewer screen. A driver's error message is deliberately not recorded, because a database error can carry row values inside it, such as the key value in a duplicate-key violation, which would smuggle row data into a store that must not hold any. Entries are written only after an operation has been attempted, so a cancelled command, a command refused before reaching the database, and any read all leave no entry, while a refused write is recorded as a failure. A history that cannot be written is surfaced to the user rather than turning a completed write into a reported failure. Updated docs/15-data-model.md.

2026-09-10, Phase 1 (T12): built the production flag's extra confirmation step, with the gate matched to what each operation puts at risk. Reason: docs/11 required an extra deliberate step before a destructive command runs against a flagged connection, and a single record-count gate would have been wrong for two of the four destructive operations. A schema change now asks for the table's name, since a count says nothing about the structure a drop destroys and is meaningless when the table is empty; a delete or update of no records or one asks for the word CONFIRM, since typing "0" or "1" is a keystroke rather than deliberation. The step is derived when the preview is built, from the count the user is looking at, and re-derived when a command is edited. It is enforced in the confirmation engine, not only in the interface, and a wrong entry leaves the preview on screen instead of discarding it. Updated docs/11-production-safety-flag.md and docs/12-ui-ux-guidelines.md.

2026-09-10, Phase 1 (T11): added DROP TABLE and TRUNCATE, previewed as a table rather than as a list of records. Reason: docs/04-database-adapters.md requires a schema change to show the affected table's current schema and row count, which is a different question from which records match a filter, so the preview now carries one of two shapes rather than pretending a dropped table is a set of rows. A drop also warns that the structure goes with the data, since a record count alone describes half of what is lost. A condition on a schema operation is refused rather than silently widened, because "truncate users where active is false" empties the whole table. Both run in a transaction, which Postgres supports for DDL, and both report the previewed row count, since Postgres reports no affected rows for DDL and saying zero after emptying a table would be wrong. "Delete table users" now parses as a drop rather than being rejected. Updated docs/04-database-adapters.md and docs/12-ui-ux-guidelines.md.

2026-09-10, Phase 1 (T10): added INSERT and UPDATE, through the same preview-then-execute loop as DELETE. Reason: the roadmap's phase 1 covers the confirmation workflow for writes, and these are the two remaining row operations before the schema operations in T11. Both reuse T7's approval guard and T8's state machine unchanged, and both bind values through the same schema-typed logic as filters, so a preview and the write it describes cannot disagree. An insert previews the exact record to be created, showing every column so defaults and nulls are visible, and reads nothing from the table's data. An update previews the matching records via the equivalent SELECT. Case folding is applied to comparisons only: a filter matches case-insensitively, but a write stores exactly what was typed. Classified update as destructive for the production flag, since it overwrites values docs/07 treats as recoverable data loss, and insert as not destructive. Updated docs/04-database-adapters.md and docs/11-production-safety-flag.md.

2026-09-10, Phase 1 (fix, before T10): made filter parameters schema-typed and text matching case-insensitive. Reason: two bugs found testing the T9 build, with one root cause. A filter on an integer column failed with "error serializing parameter 0", because a Rust i64 was bound against an int4 column; this was the same bug as T3's date failure, which had been fixed narrowly for dates instead of generally. And text filters were case-sensitive, so "Alan Turing" matched where "alan turing" did not. Both came from the query builder never being given the column types describeSchema had already read. It now receives the target table's columns and binds each parameter natively where an exact type exists, casts the parameter (never the column, so indexes still apply) where it does not, and compares as text for exotic types. Text equality now folds case in the comparison only, leaving the stored and typed values untouched. Preview and execute share the builder, so both are fixed together and cannot disagree. Updated docs/04-database-adapters.md.

2026-09-10, Phase 1 (T8): added the confirmation engine, implementing docs/05-confirmation-workflow.md steps 4 through 10. Reason: the adapter guard from T7 makes execution without a preview impossible, but something still has to run the sequence, route reads past confirmation, and turn an edit back into a new preview rather than an execution. The sequence is expressed as types rather than a status field: a pending write only exists after a successful preview, is consumed by whichever of confirm, edit, or cancel is chosen, and edit returns a fresh pending write instead of a path to execute. 2026-09-10, Phase 1 (T7): added the Postgres DELETE preview and its guarded execute, the core safety loop at the adapter layer. Reason: docs/05-confirmation-workflow.md's rule that no write runs without a preview is the reason this product exists, and enforcing it by convention would mean every future adapter has to remember. `execute` now accepts only an `ApprovedWrite`, obtainable solely by consuming a `Preview`, which only an adapter can construct by actually querying the database, so executing without a preview does not compile. The preview's WHERE clause and the delete's are built by the same function from the same filter, so they cannot drift. Writes run inside a transaction per docs/04. Also removed `#[non_exhaustive]` from `Operation`: adding an operation should break every match in the workspace and force each to be handled deliberately, rather than letting a new destructive operation inherit a safe one's catch-all arm. 2026-09-10, Phase 1 (T6): added the Intent domain model and the rule-based parser for reads and deletes. Reason: the confirmation workflow works from a structured intent, not raw text, and every operation after this one extends the same model. 2026-09-10, Phase 1 (T5): added the Postgres adapter's connect, describe schema, and health check, the shared `Adapter` trait, and the `Schema` types the parser and preview screen will read. 2026-09-10, Phase 1 (T4): added the connection config store, plus the shared `Secret` and `Engine` types it depends on. Reason: every later task needs somewhere to read connection details from, and the production flag needs somewhere to persist. Credentials are plaintext, which docs/06-credential-vault.md permits until phase 4, so three things limit the damage without pretending to be a vault: `Secret` redacts itself in Debug output and has no Display impl, so a password cannot reach a log or panic by accident; the file is owner-only on Unix; and saves are atomic so an interrupted write cannot truncate the connection list.
