# Changelog

Conventions: docs/21-changelog-conventions.md. One entry per distinct change, newest at the top.

2026-09-10, Phase 1 (fix, before T10): made filter parameters schema-typed and text matching case-insensitive. Reason: two bugs found testing the T9 build, with one root cause. A filter on an integer column failed with "error serializing parameter 0", because a Rust i64 was bound against an int4 column; this was the same bug as T3's date failure, which had been fixed narrowly for dates instead of generally. And text filters were case-sensitive, so "Alan Turing" matched where "alan turing" did not. Both came from the query builder never being given the column types describeSchema had already read. It now receives the target table's columns and binds each parameter natively where an exact type exists, casts the parameter (never the column, so indexes still apply) where it does not, and compares as text for exotic types. Text equality now folds case in the comparison only, leaving the stored and typed values untouched. Preview and execute share the builder, so both are fixed together and cannot disagree. Updated docs/04-database-adapters.md.

2026-09-10, Phase 1 (T9): built the three phase 1 screens, the Tauri command layer between them and the backend, and screen-level tests with the command bridge mocked. Reason: the safety loop was complete underneath but had no interface, and the point of the loop is what a person sees before confirming. The pending write is held in the backend, not the frontend, so confirming acts on the preview MYDB actually produced rather than on something the interface hands back. The connection summary type has no password field at all, so a credential cannot travel to the interface even by mistake. Two interface bugs found by the tests: editing a command left the screen in its edit form instead of showing the revised preview, and two different buttons were both labelled Edit. Updated docs/12-ui-ux-guidelines.md and docs/18-testing-strategy.md.

2026-09-10, Phase 1 (T8): added the confirmation engine, implementing docs/05-confirmation-workflow.md steps 4 through 10. Reason: the adapter guard from T7 makes execution without a preview impossible, but something still has to run the sequence, route reads past confirmation, and turn an edit back into a new preview rather than an execution. The sequence is expressed as types rather than a status field: a pending write only exists after a successful preview, is consumed by whichever of confirm, edit, or cancel is chosen, and edit returns a fresh pending write instead of a path to execute. Also refactored the preview onto a shared `RecordSet`, so the DELETE preview and a plain read are literally the same query code and cannot drift apart. Added a `test-support` feature for constructing previews without a database, verified as unreachable from the application build. Updated docs/05-confirmation-workflow.md.

2026-09-10, Phase 1 (T7): added the Postgres DELETE preview and its guarded execute, the core safety loop at the adapter layer. Reason: docs/05-confirmation-workflow.md's rule that no write runs without a preview is the reason this product exists, and enforcing it by convention would mean every future adapter has to remember. `execute` now accepts only an `ApprovedWrite`, obtainable solely by consuming a `Preview`, which only an adapter can construct by actually querying the database, so executing without a preview does not compile. The preview's WHERE clause and the delete's are built by the same function from the same filter, so they cannot drift. Writes run inside a transaction per docs/04. Also removed `#[non_exhaustive]` from `Operation`: adding an operation should break every match in the workspace and force each to be handled deliberately, rather than letting a new destructive operation inherit a safe one's catch-all arm. Updated docs/04-database-adapters.md and docs/18-testing-strategy.md.

2026-09-10, Phase 1 (T6): added the Intent domain model and the rule-based parser for reads and deletes. Reason: the confirmation workflow works from a structured intent, not raw text, and every operation after this one extends the same model. A filter holds typed values rather than query text, so there is nowhere for user input to become syntax; a test asserts an injection attempt survives as an ordinary text value. Two bugs found and fixed while writing the tests: operation detection scanned the whole command for the word "table", so an ordinary value could turn a row delete into a rejected DROP TABLE; and lowercasing the whole command silently case-folded values, corrupting emails and names. Both now have regression tests. Updated docs/10-nlp-voice-and-local-model.md.

2026-09-10, Phase 1 (T5): added the Postgres adapter's connect, describe schema, and health check, the shared `Adapter` trait, and the `Schema` types the parser and preview screen will read. Reason: every later phase 1 task needs a live connection and a known schema to work against. Connection parameters are set on the driver's config builder rather than formatted into a connection string, since a password containing a quote or equals sign would corrupt a hand-built string and could surface fragments of itself in the resulting parse error. The trait exposes no execute function yet, so there is no window in which an adapter could execute without the preview guard that arrives with it in T7. Schema lookup returns nothing for an ambiguous table name rather than guessing, since silently picking one could target the wrong table. Updated docs/04-database-adapters.md.

2026-09-10, Phase 1 (T4): added the connection config store, plus the shared `Secret` and `Engine` types it depends on. Reason: every later task needs somewhere to read connection details from, and the production flag needs somewhere to persist. Credentials are plaintext, which docs/06-credential-vault.md permits until phase 4, so three things limit the damage without pretending to be a vault: `Secret` redacts itself in Debug output and has no Display impl, so a password cannot reach a log or panic by accident; the file is owner-only on Unix; and saves are atomic so an interrupted write cannot truncate the connection list. A malformed file is reported as an error rather than treated as an empty list, since silently discarding a list we failed to parse would lose the user's saved connections. Updated docs/15-data-model.md and docs/06-credential-vault.md.

2026-09-10, Phase 1 (T3): added a Docker Postgres test instance, an exact seed fixture, control scripts, and the CI integration job that runs against the same image. Reason: docs/18-testing-strategy.md requires adapter correctness to be proven against a real engine, and every adapter task from T5 onward depends on known-good data to assert previews against. The image is pinned by digest so a retagged upstream cannot change what tests run against, and the CI job fails if no integration test actually executed, so a silently empty suite cannot look like a pass. Updated docs/18-testing-strategy.md and CLAUDE.md.

2026-09-10, Phase 1 (T2): added a GitHub Actions matrix that builds and tests the app on Windows, macOS, and Linux on every commit, plus a dependency audit job. Reason: development happens on a macOS machine only, so without this, Windows and Linux breakage would go unseen until phase 3. Actions are pinned to commit SHAs rather than tags, since a tag is mutable and a compromised upstream tag could otherwise alter the build silently. Integration and end-to-end jobs are Linux-only for reasons recorded in docs/18. Updated docs/03-phases-roadmap.md and docs/18-testing-strategy.md.
